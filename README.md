## 📌 프로젝트 소개

### 왜 만들었나
한강공원은 주말·공휴일마다 주차 대란이 벌어집니다. 하지만 방문 전에 **"오늘 이 주차장이 얼마나 붐빌지"**를 미리 알 방법이 없어, 헛걸음하거나 오래 헤매는 일이 많습니다.

그래서 과거 이용 데이터를 학습해 **날짜별·주차장별 혼잡도를 예측**하고, 미리 **예약**까지 할 수 있는 서비스를 만들었습니다.

### 한 줄 요약
`날짜와 주차장을 고르면 → ML이 혼잡도를 예측하고 → 잔여 면수를 알려주며 → 예약할 수 있는 서비스`

**전체 흐름**
1. 사용자가 날짜·주차장 선택
2. 프론트엔드가 `/predict` API 호출
3. FastAPI가 날짜에서 피처(요일·주말·공휴일 등) 계산
4. ML 모델이 혼잡도(%) 예측
5. 잔여 면수 계산 후 응답 → 화면 표시
6. 사용자가 예약하면 DB에 저장

## 🤖 ML 학습 파트

이 프로젝트의 핵심 — **주차장 혼잡도 예측 모델**

### 전체 학습 로직

<!-- 이미지 다이어그램으로 교체하면 더 좋습니다: ![ML 파이프라인](docs/images/ml_pipeline.png) -->

### 무엇을 예측하나
날짜와 주차장을 입력하면 **혼잡도(occupancy_pct, %)**를 예측하고, 이를 바탕으로 잔여 주차면수를 계산합니다.

### 데이터
- 출처: 서울 열린데이터광장 (한강공원 주차장 일별 이용 데이터)
- 주차장별 일별 이용 대수(`daily_count`)와 총 주차면수(`capacity`)로 혼잡도 산출

### 피처 (Feature)
날짜 하나에서 아래 피처를 자동 생성합니다.

| 피처 | 설명 |
| --- | --- |
| lot_id | 주차장 ID |
| capacity | 총 주차면수 |
| month | 월 (1~12) |
| day_of_week | 요일 (1~7) |
| is_weekend | 주말 여부 (0/1) |
| week_of_year | 연중 주차 (1~53) |
| is_holiday | 공휴일 여부 (0/1) |

### 평가지표
회귀 모델이라 아래 지표로 예측 성능을 측정했습니다. (혼잡도 % 예측)

| 지표 | 의미 | 특징 |
| --- | --- | --- |
| **RMSLE** | 로그 변환 후 RMSE | 값의 범위가 넓을 때 상대 오차를 동등하게 평가 (주 지표) |
| **RMSE** | 평균 제곱근 오차 | 큰 오차에 민감, 예측이 얼마나 벗어나는지 |
| **MAE** | 평균 절대 오차 | 실제 오차의 평균 크기를 직관적으로 |
| **R²** | 결정계수 | 모델이 데이터를 얼마나 설명하는지 (1에 가까울수록 좋음) |

> 💡 **주 지표는 RMSLE**입니다. 예측·실제값에 로그를 씌워 계산해서, 혼잡도처럼 값의 범위가 넓은 데이터에서 큰 값과 작은 값의 **상대 오차를 공평하게** 평가합니다.

### 최종 모델

- 시계열 데이터라 **시간순으로 정렬 후 분할** (무작위로 섞으면 미래 정보가 학습에 새어 들어감)
- 실험 추적: **MLflow**로 모델·파라미터·성능을 기록·비교 <!-- 사용했다면 유지 -->
- `joblib`으로 저장(`models_pkl/hangang_parking.pkl`) → 서버 시작 시 로드 → `/predict`마다 즉시 예측

### 📊 MLflow로 실험 관리

여러 모델과 파라미터를 실험하다 보면 **"어떤 설정에서 성능이 가장 좋았는지"** 기억하기 어렵습니다. 그래서 **MLflow**로 모든 실험을 자동 기록·비교했습니다.

**MLflow란?**
머신러닝 실험을 추적·관리하는 도구입니다. 모델을 학습할 때마다 **어떤 파라미터로 학습했고, 성능(지표)이 얼마였는지**를 자동으로 기록해서, 나중에 실험들을 한눈에 비교하고 최적 조합을 찾을 수 있습니다.

**우리가 MLflow로 기록한 것**
| 항목 | 내용 |
| --- | --- |
| Parameters | 모델 종류, 하이퍼파라미터 (n_estimators, max_depth 등) |
| Metrics | RMSLE, RMSE, MAE, R² |
| Artifacts | 학습된 모델 파일, 시각화 자료 |
| 실험 비교 | 여러 run을 나란히 비교해 최고 성능 조합 선택 |

## 🚀 설치 및 실행

```bash
# 1. 저장소 복제
git clone https://github.com/아이디/저장소명.git
cd 저장소명

# 2. 가상환경 생성 및 활성화
python -m venv venv
source venv/bin/activate      # Windows: venv\Scripts\activate

# 3. 패키지 설치
pip install -r requirements.txt

# 4. 환경변수 설정 (.env 파일 생성)
# DB_HOST, DB_PORT, DB_USER, DB_PASSWORD, DB_NAME
# SECRET_KEY, KAKAO_API_KEY 등

# 5. 서버 실행
python main.py
# → http://127.0.0.1:8000
```

> ⚠️ `.env`, `models_pkl/`, `__pycache__/` 등은 `.gitignore`로 제외되어 있습니다.
> ML 모델(.pkl)이 없으면 예측 API가 동작하지 않으니, 학습 노트북을 먼저 실행하세요.

## 🔧 트러블슈팅 (ML 학습 중 겪은 문제)

> 발표에서 "이런 문제를 만나 해결했다"는 스토리는 실력을 보여주는 좋은 소재입니다.

<!-- 실제 겪은 내용으로 다듬어 채워주세요. 아래는 이 프로젝트에서 흔히 겪는 예시입니다 -->

- **시계열 데이터 누수(data leakage)**: 처음에 데이터를 무작위로 섞어 분할했더니 성능이 비현실적으로 높게 나옴 → 미래 데이터가 학습에 새어 들어간 것. **날짜순으로 정렬 후 분할**하도록 수정해 실제 예측 상황에 맞춤

- **평가지표 선택**: 단순 RMSE만 보니 혼잡도가 높은 주차장에만 오차가 쏠리는 걸 놓침 → 값의 범위가 넓어 **RMSLE**를 주 지표로 도입, 상대 오차를 공평하게 평가

- **Optuna 튜닝 시간이 오래 걸림**: trial을 너무 많이 잡아 학습이 지나치게 김 → trial 수와 탐색 범위를 합리적으로 조정, 성능이 좋았던 모델 위주로만 튜닝

- **모델 저장 형식 불일치**: 학습 노트북은 모델을 번들(dict)로 저장했는데 서버는 모델 객체로 로드하려다 `dict has no attribute predict` 오류 → 로드 시 `["model"]`을 꺼내도록 수정 (학습·서빙 간 형식 일치의 중요성)

- **예측값이 범위를 벗어남**: 회귀 모델이 혼잡도를 음수나 100% 초과로 예측하는 경우 발생 → 결과를 **0~100%로 보정(clamp)**

- **앙상블이 항상 더 좋지는 않음**: 단순히 모델을 합친다고 성능이 오르지 않음 → 서로 다른 특성의 모델을 조합하고, 앙상블 결과도 **동일 지표로 검증**해 실제 개선됐을 때만 채택

## 🚀 배포 (Railway)

> 배포 과정에서 겪은 문제도 있다면 여기에 간단히 정리할 수 있습니다.

<details>
<summary>배포 트러블슈팅 (접었다 펼치기)</summary>

- **Railway 502 에러**: 서버 Python 버전이 로컬(3.11)과 달라 모델 로드 실패 → `.python-version`으로 버전 고정
- **ModuleNotFoundError (lightgbm)**: `requirements.txt`에 ML 패키지 버전 명시로 해결
- **libgomp 오류**: LightGBM/XGBoost가 필요로 하는 시스템 라이브러리를 `railpack.json`에 추가

</details>
